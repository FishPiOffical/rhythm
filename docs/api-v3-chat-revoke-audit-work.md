# 聊天室撤回审计修复

## 场景与原因

用户撤回普通聊天消息后，`chat_room` 原记录会物理删除。历史经典站在删除前保存 `cr-revoke` 私有日志，举报后台可在原消息不存在时读取日志中的正文。共享撤回服务接入后，经典控制器在事务提交、消息删除之后调用 `chatroomLog`，此时重读不到原消息，旧辅助方法吞掉异常，造成审计缺失；V3 入口也没有保存正文快照。

本次继续保留物理删除，修复的是删除前审计及其事务一致性；权限、费用、每日计次、红包不可撤回规则、请求和成功回执不变。过去已删除且未留下日志的正文无法由本修复重建。

## 实现与边界

- 新旧入口共用 `ChatMessageWithdrawalMgmtService`。验证当前锁定账号、消息归属和费用后，从删除核心传入的锁定行取得原始快照，在实际删除前写入 `LogsService.addChatroomRevokeInCurrentTransaction`。
- 审计直接加入现有数据库事务，不使用会另开事务、吞错或触发公开广播的通用日志方法。审计、扣费、计次、删除事件、表态清理、职业撤销及 V3 回执一起提交或回滚。
- 保留管理消费格式：`type=cr-revoke`、`key3=消息 ID`、`public=false`；`data` 包含 `oId`、原样的 `content` JSON 字符串、当前锁定账号的 `actorId` 和 `actorName`。操作者不从客户端请求或消息作者快照取值。
- 入口沿用既有地址脱敏方法；地址只用于首笔审计，不进入幂等摘要。同键从不同地址恢复时返回原回执，不重写审计、不再次扣费和广播。
- 普通接口和 WebSocket 不增加正文快照字段。经典公开日志只取 `public=true`；V3 公开日志还有类型白名单。举报后台继续使用精确 `key3` 和旧日志 JSON ID 回退查询。
- 私信 `chat-revoke` 只记录消息编号的规则保持不变。旧 `chatroomLog` 保留源码兼容并标为弃用，当前生产撤回入口不再调用它。

## 数据库前置

原 `repository.json` 中 `logs.data` 的长度 2000 经捆绑 Latke 映射为 MySQL `TEXT NOT NULL`，并不是 2000 字符上限；但其容量仍小于 `chat_room.content` 的 `MEDIUMTEXT`。嵌套审计 JSON 还会增加转义字节，长消息快照可能超过 TEXT 的 65535 字节容量。

已将 `logs.data` 声明改为 102400，使新建表使用 `MEDIUMTEXT NOT NULL`。已有数据库须先备份、核对实际表前缀，在低峰执行 `sql/20261114_chat_revoke_audit.sql`，再启动新代码；合并脚本也已追加相同语句。迁移保留列的字符集、排序规则、空值、默认值和注释；MEDIUMTEXT/LONGTEXT 跳过，不降低更大容量，不改写日志内容。缺少原表或字段会明确失败。DDL 可能等待元数据锁或重建表，需要按实际库安排维护窗口。

本轮未连接运行库、未执行该迁移，也没有以截断快照或忽略审计失败规避容量不足。

## 人工验收

当前状态：待人工验收，本地提交不代表可以合入或发布。先按上节完成隔离本地库迁移，核对 `logs.data` 为 MEDIUMTEXT 或 LONGTEXT，再由开发者在 IDEA 重新编译/重启 Rhythm，按以下步骤验证，不操作线上消息：

1. 使用本地普通账号发送两条消息。分别从经典站和 V3 撤回，确认费用仍为当日既有序列，列表、详情和订阅均不再显示已撤回正文。
2. 由另一测试账号先举报待撤回的普通消息，撤回后以有权限的管理账号访问 `/admin/reports`，确认仍能读取对应消息快照；核对日志仅一条、非公开，作者与撤回操作者没有混淆。
3. 使用 OP/管理员撤回他人普通消息，检查原有免计次/免费规则；普通账号撤回他人、第三方令牌管理撤回和任意角色撤回红包仍应拒绝。
4. 对同一 V3 原键重复提交（含响应丢失后恢复），确认回执一致，无额外日志、积分扣款、每日计次和广播。
5. 在隔离测试环境注入日志写入或后续提交故障，确认消息、表态及余额保留；恢复存储后用原键再试，只有一次成功记录。不要为此关闭线上数据库或改动真实审计权限。
6. 游客/普通用户查看公开日志、聊天历史和详情，不应拿到撤回审计中的原文。PC/移动端沿用同一后端入口，均需核对撤回结果。正常情况下不新增验证码；若环境触发现有验证码，仍由人工完成原有流程。
7. 在隔离 MySQL 库使用允许的长消息/历史长消息夹具，撤回后比对日志快照与删除前 UTF-8 字节及原字符串，确认完整且未截断；重复执行迁移不应改写日志或降低 LONGTEXT 容量。自动用例已验证字段映射，真实 MySQL DDL、并发与长度仍待本步骤验收。
