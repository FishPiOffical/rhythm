## 范围与行为

用户于2026-11-16明确同意实施这三项后端调整。前端单帧事件协议、旧版apiKey/Session身份、验证码策略及调用位置保持不变。本次无需执行 SQL，无新增表、字段、依赖或迁移。

1. 新站携带Cookie访问时，沿用 `WebsiteLoginCookies` 已有精确可信来源规则。第三方网页使用Bearer及 `credentials: omit` 调用业务接口；OAuth实际响应仍核对应用登记来源。其他来源不获得跨源凭据读取许可。
2. 同一访问令牌连续请求时，每次仍读取当前令牌、客户端与用户；只将近似活动时间写入合并到一分钟。成功提交才记入节点活动缓存，失败可重试；条件SQL不覆盖撤销、失效或其他授权字段。分段锁竞争允许略过该次活动记录，因此活动时间不能用于授权或精确审计。
3. 同一批聊天室事件先检查序列，再去重读取消息及reaction。每20个消息一组查询，每条保留原有2001行探测上限；超过2000条仍按原协议省略实时表态快照。事件数、revision和发送顺序不变，每帧仍为一个对象。快照只在本批复用，按连接补入个人选择，下一批重新查询。

## 账号安全补充复核（2026-11-17）

用户追问其他安全问题后，按当前 `f6dc5c48` 做高风险源码检查。下列前三项均位于前一提交已经存在的共享/旧版代码，不由本次CORS与性能调整引入。只核对路由及控制流，不发送真实业务请求、不修改业务代码，不把源码结论等同于生产利用成功。

1. **高优先级：旧版MFA解绑缺少二次证明。** `MFAProcessor.java:72` 注册GET `/mfa/remove`，只接 `LoginCheckMidware`；`:133` 方法直接清除两步验证配置后调用普通用户更新，没有二次身份验证、CSRF或来源校验，也未接新版凭据全撤。已有登录会话或旧apiKey可关闭MFA；跨站顶层GET导航还可能携带Lax Cookie触发关闭两步验证的操作，是否成功受实际Cookie及全局风控影响。CORS不阻止浏览器发送导航请求。
2. **高优先级：MFA配置读取异常按未启用处理。** `UserQueryService.java:746` 的配置查询捕获RepositoryException后返回空字符串，`MFAProcessor.java:165` 将空配置直接判为验证通过；`LoginProcessor.authenticate` 调用此方法，V3也复用该登录逻辑。风险前提是攻击者已知密码，MFA配置读取失败而随后凭据校验及发行仍可成功；全库持续故障通常会在其他步骤阻断，不能据此宣称数据库一故障就必然能登录。
3. **高优先级：错误MFA不消耗登录失败额度。** `LoginProcessor.java:722` 在密码正确而MFA错误时提前返回，`:736` 的失败累计只覆盖密码错误；`MFAProcessor.verifyLogin` 无额外账户级尝试预算。已知密码的攻击者可持续猜测动态码，仍受通用CC/验证码防护限制，但缺少与目标账户绑定的MFA错误限制，分散来源可能增加尝试。未做爆破或压测。
4. **中优先级：旧验证页面暴露完整手机号。** `LoginProcessor` 将按code查到的用户交给reset-pwd/register2模板，PC/移动均直接输出 `user.userPhone`。页面元数据读取仍使用只按code查询的 `getVerifycode`，未限定用途、接收者和有效期；完成写入的新版验证核心有更严格校验，不能把信息泄露直接等同于任意重置。此项在原访问控制专题已记为用户知情暂不修。
