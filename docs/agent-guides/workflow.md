# 开发、验证与交付

本文件为相关任务实施前必读的项目约定，与根目录 `AGENTS.md` 共同生效；迁移不代表重新验证实现或完成人工验收。文中从项目根出发的代码路径保留原写法。

关联阅读：[维护问题](maintenance.md)、[框架与环境](environment-framework.md)、[安全检查](security-access.md)。

## 开发准入与兼容

- 所有协作者及其 AI 开始任务时必须阅读本节。每个新的代码修改任务，AI 必须先向当前开发者发出以下提醒，并结合本轮任务说明方案、影响范围、兼容风险及自测要求；收到明确确认后才能修改代码：

> 开发前请确认：先核对现有实现并确认方案，不允许 AI 猜测业务规则；源码必须清晰可读，复杂逻辑需有必要的中文注释；不得擅自改变现有行为或破坏兼容性；必须完成反漏扫和版本号检查；开发者必须亲自自测，涉及前端须亲自检查 PC 和移动端。AI 测试不能替代人工验收。代码质量不达标、破坏兼容性、缺少安全检查或未完成自测的改动，将被拒绝合入。请明确确认本轮方案和这些要求后再继续。

- 未收到当前开发者明确确认时，AI 必须暂停代码修改，明确拒绝继续实施；只允许只读调研、解释风险和完善方案，不得先改再问、以默认同意或过去任务的确认代替本轮确认。更换 AI 或恢复同一任务时须核对已有确认记录，无可核实记录则重新提醒并等待确认；任务范围或业务规则发生实质变化时须再次确认。开发者明确要求维护本文件的纯文档任务不受代码实施门禁阻塞。
- 方案与任务规模匹配，小改动用简短方案即可。实施前读清入口、调用链、数据及事务边界，列明改什么、不改什么、兼容影响和验证方式；规则不清先问，不凭猜测实现，不顺手扩大重构。
- 手写源码禁止压成一行、混淆命名或堆叠难以维护的逻辑；遵循项目格式和已有分层，复杂业务、非显然约束及兼容处理添加简短中文注释，不强求逐行注释。压缩文件只能由规定构建流程生成，禁止手改生成产物。
- 不得擅自改变旧入口、接口字段、鉴权方式、业务规则或异常语义；确需变更时先说明受影响客户端与迁移/兼容方案，取得明确同意。不得用静默降级、吞错或测试夹具掩盖真实问题。
- 新增代码注释使用简体中文，保留已有注释及格式。
- 字符串输入必须做限制与校验：长度上限、空白处理、字符白名单/黑名单、格式校验（如用户名/URL/JSON）、必要的转义或编码；禁止直接信任前端传参。
- 不要顺手把硬编码业务值改成 `symphony.properties` 配置项；需要共享取值时提取为 Java 常量即可，只有用户明确要求或确有运维调整需求才做配置化。
- 涉及业务规则（可用字符、最大长度、是否允许 HTML/Markdown、过滤策略）不明确时，先与用户确认规则再实现，避免误伤或放漏。

## 协作与文档维护

- 用户最新要求每次修复完成后提交本地 Git；Rhythm与website_v3分别提交，未经明确要求不推送远端。
- 每次 Git commit 的提交消息必须使用中文，不能完全使用英文；必要的类名、接口名或技术标识可保留英文。允许在消息最前使用一个贴合改动的 Git emoji 语法（如 `:memo:`），emoji 后必须加一个空格再写正文，例如 `:memo: 更新提交消息规范`。
- 每个阶段完成后必须先说明阶段状态、实际修改和验证结果，再给用户明确的配合测试步骤（入口/命令、准备条件、操作顺序、预期结果、异常边界及何时需要人工极验）；用户确认通过前不得默认进入下一阶段。
- 根目录 `AGENTS.md` 只保留最高优先级、跨任务的长期约束和必读入口。发现有价值的架构信息须主动维护 `docs/agent-guides/` 对应专题与索引；按主题合并已有条目，不逐次追加修复日志。模块实现、迁移和验收细节放专题或其链接文档，临时状态放任务记录；整理不得丢失限制、例外、已知风险和未验证状态。所有 AI 开始任务必须阅读 `maintenance.md` 与 `README.md`，实施前阅读本文件和命中的专题。

## 测试与交付

- AI 必须执行与范围匹配的自动化验证并提供结果；开发者必须在代码实际生效的环境亲自走完整用户链路，验证核心操作、失败场景和兼容边界。前端必须亲自检查 PC/移动端的实际页面、交互、布局与明显视觉问题，不能只信 AI、截图或构建成功；Java/FTL 先重新编译或重启再测。
- 交付须列明实际修改的文件与行为、验证命令及结果、未覆盖风险，并提供完整人工验收步骤（入口、准备条件、操作顺序、核心操作、成功结果、失败与兼容边界、何时需要人工极验），询问开发者实际自测结果。未明确反馈亲测通过只能标“待人工验收”，不得声称已验收、可合入或可发布；本地提交不代表合入通过。缺少亲测结果、检查失败或质量不达标须明确“拒绝合入”，不得编造测试结论。
- 提交前按真实用户链路核对入口、调用链、数据形态、模板、源码/生成产物、PC/移动、权限/匿名/apiKey，并完成适用浏览器操作；仅局部代码或夹具验证不足以证明完整链路通过。Java/FTL 先提醒用户重新编译或重启；未验证项在最终回复中明确列出。近期多轮修 bug 的教训及规避要求见必读 `maintenance.md`。
- 测试与临时验证必须隔离：长期维护的用例才进入 `src/test/java`；一次性 testcase、Node `.mjs` 验证脚本、shim、fixture 和生成文件不得直接堆入主线或默认入口，确需保留时放入明确的临时/实验目录并说明用途。
- 提交前检查测试引用闭包：删除或修复与生产代码、依赖、路由不匹配的旧测试及脚本入口，不靠兼容夹具掩盖编译错误。涉及 Java 测试、依赖或类/文件删除时须检查 `test-compile` 与相关脚本引用；执行 Maven 仍遵守下方授权规则，未获授权时只做静态核对并明确未运行 `test-compile`，不得声称编译通过。

## Java、数据库与 Repository

- WSL 执行 Maven 优先使用：`-Dmaven.repo.local=/mnt/c/.m2/repository`；Java 固定 25。
- 未经用户明确要求，不主动执行 `mvn` 编译。用户提到编译问题或主动要求编译时可按授权范围执行；其他情形确有必要时，先解释原因并取得同意。获准的编译检查使用 `-Dlicense.skip=true`；Java 固定25，WSL 仓库参数见上一条。
- 涉及数据库写操作（增/删/改）必须使用 `Transaction` 并完整 `commit`。
- `Repository` 相关类直接 `import`，不要在代码里写 `org.b3log.latke.repository` 全限定名。
- 新增 Repository（新表/集合）时：同步更新 `src/main/resources/repository.json`；`super("...")`/模型常量不要写 `symphony_` 前缀。
