# Commit 审查门禁

本专题适用于代码审查、合并前检查和发布前复核。审查必须按提交实际影响范围逐项核对并记录证据；任何一项未检查、检查失败或无法证明时，不得写成“无问题”“已通过”或“可合入”。

## 审查清单

1. **功能与兼容性：** 从入口、调用链、数据读写、事务边界和异常路径核对是否改变原有功能逻辑；覆盖成功、失败、重试、幂等、并发、旧客户端/旧接口和回滚场景，区分明确修复与意外行为变化。
2. **硬门禁与架构约束：** 检查新增模块、路由、任务、Repository、配置和依赖是否遵循项目硬门禁，包括鉴权、CSRF、事务完整提交、锁序、缓存边界、输入校验、错误暴露、文档同步及不得绕过的保护边界。
3. **防护链路完整性：** 确认是否触碰防火墙、反漏扫、验证码盾、黑名单、来源统计或受保护调用；检查源码引用、注册/路由接线、运行时顺序、失败与解封路径、前后端及多实例链路，运行适用的指纹和保护检查，不得用改指纹或删除引用消除告警。
4. **安全与滥用：** 评估鉴权、越权、身份混淆、会话/令牌边界、CSRF、XSS、SQL/命令注入、SSRF、路径穿越、反序列化、开放重定向、批量滥用、资源耗尽、竞态和重放；确认外部输入有格式、长度、字符和枚举校验，输出按上下文编码或白名单清洗。
5. **公开数据与隐私：** 所有 API、模板、日志、事件、审计、错误和管理页面均按最小字段白名单输出；不得采用“屏蔽密码和手机号即可”的黑名单方式暴露用户对象，必须逐字段确认用户名、个性签名、联系方式、位置、角色、内部 ID、令牌、原文及审计数据的可见范围、脱敏和访问权限。
6. **数据、迁移与一致性：** 核对 SQL 是否幂等、兼容目标数据库版本、表前缀和既有字段属性，是否需要备份、锁窗口和回滚；核对模型、Repository、`repository.json`、索引、种子数据和迁移脚本一致，并确认写入、审计、缓存、异步副作用在提交前后不会部分成功。
7. **接口与客户端影响：** 检查 API 文档、`UPDATE_LOG.md`、状态码、字段、鉴权 scope、幂等语义和错误码是否同步；评估 PC/移动端、旧客户端、第三方调用、生成产物、CDN/source map、配置和依赖升级影响，不能只审源码单端。
8. **可观测性与故障处置：** 检查日志是否足以定位失败且不泄露秘密，异常是否保留并正确传播，超时、重试、降级、告警、回滚和未知提交结果是否有明确语义；禁止吞错、假成功、静默降级或用测试夹具掩盖生产故障。
9. **验证证据与结论分级：** 至少完成与范围匹配的静态检查、专项测试和真实链路核对；明确区分“发现问题”“未发现问题但门禁未完成”“检查通过”“待人工验收”，列出未运行的测试、环境限制和残余风险。审查回复先按严重度列 findings（含文件和行号），再说明功能、证据和未覆盖项。

## SQL 输出要求

- 只要提交新增、修改或删除数据库结构、索引、字段、数据种子或迁移步骤，审查和交付时必须把本次需要执行的全部 SQL 汇总成一段可直接复制到 MySQL 客户端的完整脚本，按执行顺序排列，并标明文件来源。
- 汇总脚本必须包含本次范围内所有必需 SQL，不得只给零散文件名、伪代码或省略语句；若存在多个脚本，按依赖顺序合并并去除重复执行内容。
- 脚本前后必须注明备份、事务、锁窗口、表前缀、数据库版本、幂等性和失败处理要求；无法确认安全重复执行或需要人工替换的部分必须明确标注，不能把未验证脚本写成可直接执行。
- 若本次不需要执行 SQL，明确写出“本次无需执行 SQL”。
