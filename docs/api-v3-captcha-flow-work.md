## 已确认实施内容

### 第 2 步：后端持续挑战和明确响应

- [x] V3 触发既有首访或周期规则后进入同 IP 的持续待验证状态；后续业务请求在服务端极验确认前持续受限，消除当前只拒绝当次请求的缺口。
- [x] V3 以统一 JSON 错误提供机器可识别的验证码业务码`captcha_required`，与普通登录失效错误区分；当前为HTTP403、`{code,msg,data:null}`，已记入接口文档。
- [x] 既有全局黑名单检查同样能向 V3 返回明确挑战；保留旧站页面 `/test` 展示与 `POST /validateCaptcha` 的服务端极验验证、成功清理流程，失败不能解封。
- [x] 验证组件加载、验证提交及必要的跨域响应可达，不被自身的持续挑战挡死；不通过移动/删除全局防护或普遍放行业务请求实现。
- [x] 同步 `API.md`、`UPDATE_LOG.md`、盾说明、受影响回归和经复核的保护版本/指纹；公开 API 文档不披露内部触发阈值与防扫描策略。

### 第 4 步：前端统一极验与队列恢复

- [x] 请求层识别明确验证码错误并复用 `RiskCaptchaGate`，保留对旧 `/test` 重定向的必要兼容；不将所有 401 当成验证码。
- [x] 修复首页队列将验证码转成 `home_reads_paused`、且队列调用在统一恢复 `try/catch` 之外的两个问题；保留与验证码无关的既有错误策略。
- [x] 同页面并发请求共享一次验证；验证期间后续受影响业务请求等待，验证本身不被业务/凭据队列阻塞；防止验证成功后迟到的旧拦截响应重复打开弹窗。
- [x] 成功后按队列恢复，原请求最多自动重试一次；取消、供应商故障、校验失败、请求中止、离页和身份变化保留明确结果，不无限循环。
- [x] 写请求只有在确认因前置验证码拦截而未执行业务、并核对原幂等键/请求体及身份边界后才进入适用恢复路径；连接失败或未知提交结果不能借验证码恢复自动重发。

### 第 5 步：SSR 与实时连接

- [x] SSR 预取受限时保持可恢复的页面状态，由浏览器针对自身来源核实并完成验证；避免把 SSR 服务器 IP 的限制误当用户 IP 限制、或用浏览器通过结果假装服务器已解封。
- [x] 核对 SSR 预取、共享公共缓存、水合与浏览器重读，验证码失败不能以空数据假成功；不把跨请求共享的 SSR 风控状态误传播成每个访客的挑战。
- [x] 源码不合成客户端身份，SSR白名单不扩大至浏览器；实际部署可信代理与IP核对仍待人工验收。
- [x] 解封后实时订阅通过既有票据与重连恢复；不得绕过实时黑名单检查，也不得仅凭 HTTP 验证通过宣称连接已恢复。

2. 使用确认无同IP登录豁免、未加白的来源访问旧站 `/`，应进入 `/test`；另一个无豁免来源访问新版首页，应显示一次正在进行的验证，网络中业务403为 `captcha_required`，后续读取等待。无痕窗口不等于新来源。
3. 取消或失败后仍受限，同一批排队任务不反复开窗；显式重试可重新验证。供应商不可达应显示失败，不得解封。携带Origin的OPTIONS只204，实际业务仍403。
4. 完成真实GeeTest4后确认 `POST /validateCaptcha` 服务端响应code0，首页原任务最多重试一次恢复；写请求只选安全可撤销操作核对原键/体，未知结果不自动重发。验证期间离页、取消或换号后旧请求不回填。普通401不能弹验证码。
5. 验证成功后订阅须重新取票并收到WS ready；单凭HTTP成功不算连接恢复。独立观察SSR服务器与浏览器来源，SSR受限但浏览器不受限时不得强迫访客验证；浏览器验证不声称服务器已解封。
6. 在PC和移动端分别检查弹窗可见、取消/失败/恢复、首页和实际业务；旧站仍可完成极验与跳回。按请求计数不变，读取多个模块后仍可能很快再次周期验证。记录实际结果后才决定合入/发布。
