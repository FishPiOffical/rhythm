# 举报后台正文安全渲染

## 原因与修复范围

`ReportQueryService.getReports` 原本会先清洗举报备注，再用未清洗的聊天原文覆盖 `reportMemo`。现存聊天和撤回快照都经过这一分支；PC、移动端 `admin/reports.ftl` 均直接输出该字段，正文或作者快照中的 HTML 因而可能成为可执行页面内容。

现在两个聊天来源共用 `renderChatReport`：作者单独按纯文本转义，正文交给现有 `Markdowns.toPrivateHTML` 本地解析并按白名单清洗。撤回提示在正文之外保留。没有日志或日志损坏时仍显示原来的提示，但其中消息 ID 必须转义；跳转链接中的 ID 作为查询参数编码，不直接拼进 HTML 属性。

本次只改变后台读取和展示，不修改原消息、撤回日志、撤回事务、举报写接口及审核权限。普通非聊天举报继续使用原有备注渲染链路。两端模板继续接收安全 HTML，避免模板再次转义导致图片、链接和 Markdown 变成标签文本。

## 正常显示与安全边界

- 保留中文、Unicode 表情、普通 Markdown、软换行、段落、图片、链接、引用和代码；已有基本 HTML 同样经过白名单处理。
- 作者名中的 HTML 或 Markdown 只作为作者文字，不参与正文解析；代码块中的标签保持代码文字。
- 图片的合法 HTTP(S) 地址及查询参数保留；不重新生成签名或改写原存储地址。
- 脚本、事件属性、危险 URL 协议、表单及嵌入式活动内容不进入输出 HTML。任意内联样式和历史交互标签不保证保留，不为恢复这些效果放宽清洗规则。
- 聊天正文及撤回快照不进入公开 Markdown 缓存或远程转换服务。模板安全处理不替代 `/admin/reports` 原有的后台权限检查。

## 变更与安全复核

本轮没有新增路由、匿名入口或认证方式；`/admin/reports` 继续使用既有权限中间件与 `menuAdminReports` 权限。没有改 CSRF、验证码/封禁流程、上传下载、数据库写入、目录访问、静态资源版本或 source map。针对本次展示边界检查了 XSS、查询参数注入与撤回原文的缓存/远程转换泄露；权限及风控整链路只做源码复核，未在真实账号上重跑。没有执行 Maven `test-compile` 或全套测试，专项仅独立编译所用的生产源码闭包。
