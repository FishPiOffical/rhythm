# 验证码盾自动化验收工具

工具按阶段开发。第一阶段只保存配置；第二阶段才打开真实浏览器并访问服务。

## 阶段 1

不需要记 Node 命令，直接双击项目里的以下文件即可：

```text
tools\captcha-shield-e2e.cmd
```

也可以在项目根目录运行 PowerShell 脚本：

```powershell
.\tools\captcha-shield-e2e.ps1
```

脚本会显示中文菜单。选择“1”进入配置向导，“2”查看已保存配置，“3”查看网卡 IP。

```powershell
node tools/captcha-shield-e2e.mjs configure
```

向导会：

- 读取 Windows 当前网卡的可用地址；自动选择 1 个回环地址 L，并自动选择 5 个不同额外地址 A-E：优先 IPv4，再选原生 IPv6，最后选 Teredo 隧道 IPv6，不要求手工填写编号。若 IPv4 加可用 IPv6 仍少于 5 个，工具会停止并明确列出已发现地址，不伪造 IP。后续浏览器和 HTTP 测试必须支持 IPv6 字面量方括号格式，且服务端监控必须看到不同源地址。
- 业务流程固定需要 2 个账号：普通登录基线账号和管理员测试账号（必须属于 `admin/管理员` 分组）。安全监控另外固定使用 `adlered`（也须具备后台管理权限），仅在 L 地址登录；已填账号中存在 `adlered` 时直接复用，否则只补填一次密码，共保存 3 个账号。密码会直接显示在输入行，保存时使用当前 Windows 用户的 DPAPI 加密，配置保存在 `%LOCALAPPDATA%\\RhythmCaptchaShieldE2E\\config.json`，不会写入仓库。
- 只要求三项人工确认：环境、账号、IP。勾选内容完全信任，不额外请求服务检查。

如果已经保存过配置，进入配置向导时会先显示上次的端口、账号、权限组和 IP，并询问是否复用。选择 `y` 后复用账号和端口，保留仍有效的来源标签，仅为失效或重复的IP选择当前未使用地址；更新后的IP在原第三项确认中显示，不另加 checklist。

每次菜单6/7/8及`webdriver-flow`开始前，都会重新读取本机可用IP。地址未变时直接复用；地址失效时先显示“原IP → 新IP”，确认后保存并启动浏览器，不重填账号密码。拒绝更新或不足L加5个不同IP时停止，保留原配置。此步骤只核对网卡地址，不校验三项人工确认中的环境或凭据。Teredo及临时IPv6会变化，确认后再次失效仍会明确失败，本轮不会换源重试。

查看已保存的非敏感配置：

```powershell
node tools/captcha-shield-e2e.mjs show
```

只查看网卡地址：

```powershell
node tools/captcha-shield-e2e.mjs ips
```

阶段 1 不读取或保存 `jiyan.key`，也不会启动浏览器。

## 阶段 2：浏览器基础流程

基础浏览器兼容入口仍需要与本机 Chrome 主版本匹配的 `chromedriver.exe`，可以通过菜单“4. 设置 ChromeDriver 路径”保存路径。第一阶段完整业务流程不再依赖 ChromeDriver，而是启动普通 Chrome 并通过 DevTools Protocol 控制。

在项目根目录运行：

```powershell
.\tools\captcha-shield-e2e.cmd browser
```

或在菜单中选择“6. 基础浏览器流程”进行 ChromeDriver 兼容检查。菜单“5. 打开配置文件编辑”会用记事本打开 `%LOCALAPPDATA%\RhythmCaptchaShieldE2E\config.json`；编辑时必须保留 `passwordProtected`、`ipPlan` 和账号字段结构。

工具会：

- 为 L、A、B、C、D、E 分别建立独立的 Chrome 用户目录；目录位于 `%LOCALAPPDATA%\RhythmCaptchaShieldE2E\profiles`，用于保留每个源地址自己的 Cookie，不把账号密码写入日志。
- 依次打开对应地址的首页。IPv6 地址自动使用 `http://[地址]:端口/` 格式。
- 基础流程使用 ChromeDriver 的 `eager` 页面加载策略；第一阶段业务流程使用普通 Chrome + DevTools Protocol，先等待 DOM 可用；对仍在后台下载的图片等非关键资源只记录提示、不把整页测试卡死。读取浏览器当前 URL；如果服务把请求重定向到 `/test`，脚本会暂停并提示你在刚打开的 Chrome 窗口中手动完成极验，完成后会自动检测页面跳转，不需要回终端按 Enter。脚本不会模拟拖动、伪造 `/validateCaptcha` 响应或把未完成的验证当作成功。
- 顶层页面访问之间至少间隔 1.5 秒，减少连续刷新的请求压力；该间隔不限制页面附带的资源与接口请求，仍可能触发 CC。如果页面标题/正文出现 HTTP 503、`Service Unavailable` 或“服务不可用”，脚本立即失败并停止后续请求，不把 503 当成通过。
- 极验等待最长 180 秒；页面仍停留在 `/test` 会明确失败，离开后自动继续下一个步骤。
- 每次顶层页面切换都会输出简短证据：最终 URL、主文档 HTTP 状态、页面标题和正文前 80 个字符；状态来自 Chrome DevTools 的 `Network.responseReceived` 主文档事件，后台图片等静态资源不会覆盖主文档状态。证据只输出到终端，不记录账号密码。
- 菜单 7 每轮新建的 L/A/B/匿名 A 回访会话各在首次访问前清理一次 HTTP 缓存，后续访问正常复用允许缓存的页面与资源；不在每次导航或每个小节重新清理。Service Worker 仍绕过，最终 A 回访仍可按流程执行一次强刷。导航必须匹配本次主文档响应、主框架和 DOM 就绪事件，超时直接失败，不接受旧页面的 `interactive/complete`。这不会清除服务端用户/IP 缓存。若页面内 API/资源请求被全局黑名单规则重定向至 `/test`、但浏览器顶层仍停留在原页面，脚本会识别重定向并在顶层打开验证码页；预期不应进验证码的步骤也会对此失败。

阶段 2 只验证兼容入口的基础链路，不代替第一阶段业务流程。若未配置 ChromeDriver，菜单 6 会直接报错；菜单 7 不需要 ChromeDriver。

## 第一阶段完整业务流程

菜单选择“7. 第一阶段完整业务流程”，或运行：

```powershell
.\tools\captcha-shield-e2e.cmd flow
```

脚本会启动不带 ChromeDriver 自动化标记的普通 Chrome，通过 DevTools Protocol 使用已保存的两个账号和 L/A/B 三个源地址执行：

- 每次完整流程开始都会为 L/A/B 建立全新的临时 Chrome 用户目录，并清除 Cookie、localStorage 和 sessionStorage，避免上一次运行的登录态跳过登录页；同一轮流程内仍会保留各自会话，用于验证源地址切换。流程结束后会尝试删除临时目录。
- L 地址登录基线账号，访问主页 10 次和 10 个不同文章页，确认没有意外进入 `/test`。
- 登录提交后等待本次主文档响应与 DOM 就绪，再核对 PC/移动页头的当前用户名；不再只看地址跳转或任意头像。图片仍可后台加载；密码错误、账号不符、HTTP 429/503 或主文档超时均判失败并保留浏览器。
- A 地址首访必须进入 `/test`；人工完成极验后，继续访问主页和文章页，要求在 5 次内再次进入 `/test`。
- A 地址再次完成极验后登录管理员账号，重复访问确认不再跳转 `/test`。
- B 地址完成首访验证并登录管理员账号，再返回匿名 A 地址；若首次回访未进入 `/test`，按本节流程额外执行一次忽略缓存的强制刷新。首次访问和刷新各自输出 HTTP 状态、标题和内容；刷新仍未触发则失败，不继续重试。该刷新是额外的真实访问，结果不等同于“首次回访即被拦截”，不能据此证明触发原因一定是缓存。
- B 登录后会关闭原 A 管理员会话并启动一个新的匿名 A 会话，避免已登录请求绕过匿名盾；独立的 L `adlered` 会话负责逐项 `/admin/misc` 监控核对，A/B 仍使用原管理员测试账号。
- L 管理员会话在业务小节前后读取监控，匹配本轮记录及统计，并核对后台表格显示；不修改安全开关。
- 流程成功时会关闭 Chrome 并清理临时用户目录；流程失败时会断开控制连接、暂停等待确认，不会关闭已启动的 Chrome，也不会删除临时目录，并打印目录路径，便于查看失败页面、Cookie 和网络状态。按 Enter 退出脚本后 Chrome 和目录仍保留，确认现场后再手动关闭窗口并删除该目录。

文章地址从 L 地址首页实际读取；不足 10 个不同文章链接时直接失败，不伪造文章地址。所有预期的 `/test` 均会暂停等待人工极验，脚本不会模拟或伪造验证结果。

每次浏览器测试（菜单6/7/8及 `webdriver-flow`）开始前，自动打开 `Init-baseline`、`Init-admin` 两个独立普通Chrome窗口，通过 `localhost:已保存端口` 分别登录两个业务账号，精确核对身份后关闭两个窗口，再运行所选模块。无需重新填账号；监控账号仍独立准备。任一登录失败便停止，保留两个窗口，结果记录初始化FAIL、未运行模块NOT_RUN。配置、查看配置和网卡等非测试命令不会登录。

重跑前关闭旧测试浏览器；上轮遗留的验证码黑名单或管理员解封白名单仍需重启服务清除。账号的历史登录IP由上述正常登录更新，其他测试地址不得关联其他用户历史登录IP。初始化不清空封禁、不修改数据库配置，也不代替服务重启。改动仅为工具脚本时无需编译Java。

## 自选测试

菜单“8. 自选测试”支持单项和组合测试，输入编号或名称，多个用逗号分隔，`all` 运行全部已实现模块。工具显示本轮执行顺序，记住上次选择，下一轮按 Enter 复用。菜单7固定执行前3项。

| 编号 | 名称 | 范围 | 来源 |
| --- | --- | --- | --- |
| 1 | 登录基线 `baseline` | 登录后主页10次、10个不同文章页 | L |
| 2 | 验证码 `captcha` | 首访、每5次验证、登录后放行 | A |
| 3 | IP切换 `session` | A/B同账号切换，匿名A回访或一次强刷 | A、B |
| 4 | 黑名单 `blacklist` | 首页/公开页/登录/不存在文章和路径/图标/API均回到验证码，直接/test及验证后恢复 | C |
| 5 | 管理解封 `unban` | 从真实IP管理表单解封D，至少6次放行，确认管理员解封白名单原因；加白留到服务重启 | D |
| 6 | 生产只读 `readonly` | 四项设置和保存disabled、有效页面凭据提交原设置仍403且状态未变、匿名监控/自检403、结构自检 | L |
| 7 | CC压测 `pressure` | 8并发阈值内302、越界429、封禁后验证码页429、无UA418；会封禁E | E |

单选例如 `4`；组合例如 `4,5,6`。也可运行：

```powershell
.\tools\captcha-shield-e2e.ps1 -Command suite -Modules blacklist,unban,readonly
```

不必先执行未选择的模块。先以L地址的 `adlered` 会话确认监控可读，成功后才打开业务窗口；每个窗口都会输出名称、用途和地址。后台页面200不代表监控接口也可读：现有服务端额外限制监控/自检只能由 `adlered` 访问，其他管理员仍可能403。旧配置无此账号时，首次菜单7/8只追加一次密码并加密保存，保留原业务账号/IP/端口/模块选择。IP切换模块单独运行时自动准备A登录，但不把周期验证标为通过。来源仍必须是配置中严格的L加5个额外地址，E仅用于CC压测。所有模块必须在确认的本机测试服务运行，不能把生产站点用作解封/压力测试目标。

运行前关闭旧测试浏览器并重启服务清除上轮封禁/加白；工具会先登录两个业务账号恢复localhost登录IP。尤其C/D/E不能关联其他用户历史IP或之前管理员解封加白。所有验收统一使用PRODUCTION，本地也保持与生产一致，不安排DEVELOPMENT开关写入测试。三项配置确认仍以用户勾选为准，不新增启动前环境扫描；运行中的断言属于测试结果。

各小节读取真实 `/admin/security/monitor`，以执行前事件为界，匹配本轮IP、方法、路径、流程、结果及相关用户状态，检查相应统计增长，再与后台表格8列核对。旧记录、其他IP或不符结果均不能当通过；超过100条保留窗口导致缺少证据会明确失败。监控中的处理器为路由匹配名称，不代表被拦截请求实际执行了业务处理器。Windows的应用内加白通过不代表Linux ipset真实解封通过。

黑名单模块的7条拦截路径及直接 `/test` 各追加唯一 `_captcha_e2e` 查询参数，避免复用旧的302跳转；路径及服务端监控匹配仍保持原样。每项只发一次顶层请求，不通过循环刷新凑日志，子资源继续正常使用缓存。浏览器缓存/Service Worker返回的旧跳转会单独标注，不能作为本次服务端拦截证据；顶层最终进入 `/test` 和真正来自网络的验证码跳转仍照常核验。

极验完成后等待返回页面的主文档响应和 DOM 就绪，再继续测试，不等待全部图片。恢复检查访问 `/about`，按当前 `IndexProcessor.showAbout` 精确要求最终为 `/article/1630569106133`、HTTP 200 且无真实验证码重定向，同时核对本轮 `/about` 放行日志；跳到其他文章、验证码页或返回错误均失败。管理员解封的公开页检查使用相同目标。

导航会短暂观察主文档是否连续跳转，并等待已经发起的新文档；URL、HTTP、标题与正文摘要取自同一文档。页面切换造成的临时读取中断，仅在确认浏览器仍可连接后重新读取，不刷新、不额外请求。跳转到登录页仍按该步骤的预期路径判断：要求主页时不会把登录页200算通过；窗口关闭、其他协议错误、429/503和持续跳转均明确失败。该等待不代表任意延迟脚本都已执行完毕，业务断言仍须结合真实监控。

当前版本输出终端证据，并在 `%LOCALAPPDATA%\RhythmCaptchaShieldE2E\runs\cdp-suite-时间\` 保存结果、截图和PDF；失败写入原因，尚未运行模块保持NOT_RUN。文件不保存密码、Cookie、CSRF令牌或极验证明。失败现场继续保留，成功仅清理本轮浏览器目录，证据和报告保留。

## E 地址 CC 压测

双击 `tools/captcha-shield-e2e.cmd`，选主菜单8，再选测试项目7（不是主菜单7）。也可运行：

```powershell
.\tools\captcha-shield-e2e.ps1 -Command suite -Modules pressure
```

复用现有账号、端口和严格的L加5个额外IP，不需要新增账号或IP。先正常初始化两个业务账号，再以L地址的adlered登录后台读取生产模式与三个开关。E仅使用HTTP请求，不开额外浏览器；socket真实绑定E，不发送Cookie或伪造来源头，UA取自本轮普通Chrome。不跟随302，不下载图片/脚本。

1. E匿名首访必须302到`/test`且出现本轮首次访问日志；再访问`/about`确认验证码黑名单302。历史加白、已有CC封禁或错误来源都会失败，不自动清理。
2. 根据后台监控的服务端时间等待下一分钟（最多约61秒，期间打印进度、不向E请求）。CC按固定分钟计数，准备流量不计入接下来的边界断言。
3. 有效匿名阈值按现有`Firewall`规则取后台阈值与250的较小值。新分钟首请求和随后最多8并发的请求合计恰好达到该阈值，全部应302到`/test`；打印每批结果，保存每个请求的HTTP、来源地址、跳转、正文摘要和耗时。
4. 再单独发一次请求，应429，监控为`BeforeRequestHandler -> Firewall`、`cc.ban`、请求频率超限且统计增长；应先于验证码跳转。新分钟及越界监控时间必须在同一计数窗口；跨分钟、提前429、越界仍302、503、网络错误或缺少日志均失败，不重跑到成功。
5. 封禁后访问`/test`仍应429，最后不带UA访问同一路径应418。418发生在CC/验证码之前，现有代码只打印控制台日志，不写安全面板；工具读取前后面板并保存HTTP证据，不虚构418面板记录。

每个监控断言仍匹配本轮E来源、URL、处理流程、结果、统计及后台8列。结果在该模块的`pressure.requests`保留直接HTTP证据，失败照常保留L浏览器。`all`包含这项压测，按最后一项执行。该模块验证并发请求与阈值边界，不是服务器吞吐性能跑分。

E的应用封禁留到服务重启，不自动解封。Windows下服务器调用ipset可能报错属于预期，但HTTP429必须成立；结果固定标注ipset未验证。Linux系统防火墙的实际封禁/解封不属于这项Windows验收，重启Java也不会清除已有Linux ipset条目。

## 截图与 PDF 报告

菜单7/8每轮自动生成，不需要安装Word、Python或其他依赖。复用现有Chrome，在独立后台页离线打印，不替换原测试页面，不为截图补发业务或E压力请求。ChromeDriver兼容入口（菜单6、`webdriver-flow`）不生成本节报告。

| 文件 | 内容 |
| --- | --- |
| `report.pdf` | 总览、模块状态、逐项图文证据、导航及压力请求明细 |
| `report.html` | 内嵌截图的离线报告，可用Chrome查看 |
| `results.json` | 初始化、所选模块、逐项断言及`report`导出状态 |
| `evidence.json` | 步骤编号、截图索引、页面和监控证据 |
| `screenshots/` | 按步骤编号保存的原始JPG截图 |

登录身份核对、每项业务断言和周期内中间访问会留图。业务步骤同时保存业务页面与当时后台监控；后台步骤保存安全面板。E使用直接HTTP，没有E浏览器页面，报告明确标注，仅附后台截图和真实HTTP证据，不画假页面。业务截图保留当时可见区域；后台截图临时展开表格宽度，保留八列及面板上部，截图后恢复，不修改数据。图片资源可能仍在后台加载，不等待全部网络空闲。详细IP、URL、处理器、流程、身份和统计增量在图旁以文字保留，可结合原始截图放大查看。

失败时也尝试生成报告并保留全部已采集证据和浏览器现场；后续模块标为NOT_RUN。截图失败会明确标记，停止测试，不以缺少图片冒充完整证据。`report.status=PASS`只表示PDF导出成功，业务结果仍看顶层及各模块`status`；业务通过但PDF导出失败时工具也报错，`report.status=FAIL`记录原因，保留现场。Chrome全部不可连接时无法打印PDF，原始JSON和已有截图仍保留。报告页生成后关闭，原测试页不被导航或替换。

截图期间临时隐藏密码输入框，随后恢复，不清空失败现场的输入值。报告为本地文件，包含测试账号名称、IP及页面可见内容；不要把整个运行目录发布为网站静态资源。旧结果没有当时截图，工具不会补造历史截图或将其当成新一轮验收。

1. 关闭上轮测试Chrome，重启本机测试服务清除应用内封禁和管理员加白。保持PRODUCTION、三个安全开关开启、临时极验配置已就绪且运行代码最新；仍使用原来的三项确认，不额外扫描密钥。
2. 双击`tools/captcha-shield-e2e.cmd`，选择主菜单8。若有失效IP，先确认自动替换；账号密码复用已保存内容。
3. 在测试项目选择处输入`all`，按显示顺序执行七个模块。开始前两个业务账号自动通过localhost登录初始化，安全监控由独立adlered会话读取。
